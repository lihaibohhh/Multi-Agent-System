# 链路加固第一阶段：统一输出校验

## 本阶段范围

把“收到可解析的模型响应”与“接受有效业务产物”分开。章节执行器现按以下顺序处理每次响应：

1. 解析及 Schema 校验。
2. 执行业务节点提供的同步、无外部写入的校验器。
3. 记录完整的本次校验状态及已知用量。
4. 通过才返回产物；可纠正错误反馈给模型，其余错误直接安全失败。

初次调用加最多两次纠正，总共最多三次。格式错误、业务错误交替出现也共用这三次，不嵌套重试。此上限是单次 `call_model` 的上限，不是整个 Run 的调用或费用上限，也不包含 SDK 内部网络重试。

已接入的业务规则：规划的配置章节上限与父章节 ID；写作正文的引用编号；章节分析/审校的矛盾 verdict；Claim 的正文、证据摘录和来源编号；全篇审校的章节 ID。历史草稿在审校节点仍保留引用检查和原有有界改稿流程。依赖版本冲突、存储故障等不能通过模型改写解决的问题，不进入格式纠正。

## 错误与诊断

`ValidationIssue` 提供 `field`、`type`、`message`，以及适用时的 `section_id`、`source_number`。一次检查收集多处错误，不遇到第一条就结束。失败绑定只修改临时副本，不保存部分 Claim。

`BusinessValidationError` 是可分类的业务错误；未预期的校验器异常记录为 `internal_error`，不追加付费调用。诊断增加：

- `schema_status`：格式校验状态。
- `business_status`：已注册业务校验的状态。
- `accepted`：本次响应是否被调用器接受，不代表整个节点、Run 或事实核验完成。
- `retryable`、`context`：错误是否可纠正，以及所在章节/版本。

沿用私有 `research_model_attempts` 的 JSONB，无新增数据库列。记录业务失败时仍计入已知用量。旧诊断不会被补写或重新解释。纠正提示最多列出 20 项错误；日志/公开异常仅列前 5 项及诊断 ID，不包含原始引文。完整错误保留在私有诊断中。

每次纠正保留原始任务/资料、上一次响应（最多 16,000 字符）和本次反馈，不累积全部对话历史。原始模型文本的存储/脱敏边界沿用 [模型输出与恢复说明](model-output-recovery.md)。

引文失败还提供最多 10 个原文定位窗口，每个最多 600 字符，帮助模型重新复制连续摘录。窗口可用最长相同片段定位，但绝不据此自动接受引文；重新生成后仍执行严格匹配。窗口只进入纠正提示和私有诊断，不进入公开异常/SSE，按研究内容保护。

## 引文匹配边界

优先精确连续匹配。其次仅允许可定位的少量中文排版空白差异：一个普通空格、NBSP、全角空格或单个换行，且相邻字符包含中文并满足限定的文字/标点边界。CRLF 按单个换行判断。不删除数字之间、英文单词之间的空格，不跨双换行、制表符或多空格拼接，不做编辑距离/模糊匹配，不改标点或数字。规范化后有多个候选位置时拒绝自动选择。

成功后保存原文切片，而非模型改写后的字符串；`draft_span`、`quote_span` 记录 Python 字符下标 `[start, end)` 和 `exact/layout_whitespace`。正文位置相对该版草稿，证据位置相对保存的来源 `content`，仅在模型看到的前 1000 字符内匹配。这些位置由代码重算，不信任模型提供的位置。旧产物字段为空，不伪造历史定位信息。

匹配仅证明摘录存在，不能排除断章取义，也不能证明 `statement` 与摘录的语义对应、来源可信度或事实真实性。独立语义审校仍是后续工作。

章节审校若同时返回 `pass` 和问题/补证查询，保留问题并保守改为 `revise`；全篇审校同理。不会为了得到 `pass` 清空反证。尚无“阻断问题/普通提醒”分类，因此此策略可能增加改稿次数，但不会把已报告问题忽略掉。
