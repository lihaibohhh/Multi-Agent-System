# Claim 逐条接受与局部修复（2026-10-08）

## 改造边界

保留首次批量抽取（最多 12 条关键 Claim），取消 Claim 的整批接受/整批丢弃。不是所有节点都拆成逐条调用：章节规划、依赖约束、全篇装配仍需整体一致性校验。逐字定位通过不代表语义支持或外部真实性已经证明。

## 执行与恢复

1. 每条独立执行字段、正文定位、来源定位校验。成功项写入 `claims`，失败候选、错误及稳定 slot 写入 `claim_work.pending`。每轮调用后提交 LangGraph Checkpoint，并更新业务章节快照；成功项不重新生成。
2. 局部修复只提供 pending 候选和相关片段。程序生成正文 `D:start:end`、来源 `S序号:start:end` ID；模型选择 ID，程序从当前原文回填文字及偏移，仍执行严格校验。正文和来源类型不能互换。提示明确指出“来源原文被误当正文”的情况。
3. 接受项不允许被补丁覆盖；原结论不允许偷偷替换，已知反证不能删除，不确定结论不能借定位修复升级。缺少/重复/无效补丁的项目继续待修复，不以删除问题换取通过。
4. 每章每次执行的初次抽取与局部修复共用最多 3 次调用。没有每条 Claim 各套 3 次的嵌套重试。每次已知 Token/未知预留仍计入原研究共享预算。
5. 第三次后仍有问题，先持久化成果，再由单独的 `section_claim_gate` 节点暂停 Run，原因 `claims_pending`。章节不标记为完成，下游不使用未完成章节装配正式报告。
6. 明确恢复产生新 execution 后，只重置这一小段的本次尝试计数，不清零 total_attempts、研究调用次数、Token 或未知预留；继续修 pending。选择章节继续的子 Run 也继承工作包，共用研究预算。
7. 正文、来源或版本变化使指纹失效，不能把旧定位用于新稿。新写作清除旧工作包。旧 Checkpoint 无 claim_work 时走初次抽取，不自动导入旧诊断结果。

可解析 JSON 中单条字段错误也可保留合法兄弟项。无法解析、截断、超出批量数量上限时不擅自猜测或截断成“完整结果”；传输/内部异常不伪装成可修复 Claim。字段解析失败的模型诊断仍记录 schema_failed，抢救后的实际接受/待修复状态保存在章节快照中。
