# 逐查询保存与恢复验证（2026-10-08）

## 交付范围

恢复仍从 LangGraph 失败节点开始，但检索节点内部按稳定查询标识重放持久化成果，只向外部发送未成功且有剩余尝试额度的请求。Token 和模型预算沿用第一阶段的共享研究账户，不会因这一改动清零。

实现位置：`core/retrieval.py` 是操作状态/有限重试；`runs/repository.py` 是事务与执行隔离；`retrieval/service.py` 给查询绑定参数；`retrieval/normalization.py` 负责标准化与轮内去重；`sections/workflow.py` 加章节/版本/轮次边界；`sections/artifacts.py` 保留原检索时间。

暂时依赖故障使用已有 `paused` 状态及 `dependency_unavailable` 原因，不新增第二套暂停 API。失败重试不会重新开一份预算。限额目前固定保存在每个操作的策略中：每执行 2 次、累计 4 次，无自动追加接口。

## 真实案例（不是自然超时复现）

脚本：`python -m scripts.verify_retrieval_recovery --live`，使用 multi-agent 环境，关闭 LangSmith tracing。

从历史 Run `run_7c73d441e9ac4d1b9207db1eb87261b8` 只读获取失败章节的前两条查询。独立 PostgreSQL schema 存放测试 Run 与结果，结束事务强制回滚；原业务 Run 和 Checkpoint 不恢复、不修改。

结果：

| 操作 | 第一次执行 | 恢复执行 | 累计 |
| --- | --- | --- | --- |
| 第一条真实知识查询 | 成功，3 条来源 | 从本项目数据库复用 | 1 次真实请求 |
| 第二条查询 | 注入 2 次超时后暂停 | 真实查询成功，3 条来源 | 2 次注入 + 1 次真实请求 |

整个案例约 47.48 秒。恢复前重建 Repository 和 RunBudget 对象，避免靠进程内结果变量冒充持久化重放。前后历史 Run/Checkpoint 校验值一致：`984a69b9ac24e3183d1e1d98103ebb2eccfc7477746496c32b3edef4c79da640`。测试 schema 已随事务回滚，不删除用户数据。

本次没有调用付费大模型；真实调用是两次 knowledge-service 只读检索，均通过固定关闭查询缓存的项目客户端。注入的超时仅用于验证恢复，不应解读为本次自然复现了服务 60 秒超时，更不能据此宣称知识服务性能已修复。

## 保留限制

数据库和远端 HTTP 不可能在同一事务中提交。远端成功、本地未保存的请求仍可能在恢复后重做；以保留旧预留和记新尝试的方式如实计费，不承诺 exactly-once。缓存隔离于当前 Run/章节版本/轮次/参数，子 Run 共预算但不隐式跨 Run 复用全部查询。

没有自动替用户恢复历史 Run、迁移旧预算或重启 API。部署先备份本项目数据库，再停止旧 API，使用新代码单实例启动并刷新页面；历史 v1 预算仍需明确确认迁移。单查询 4 次耗尽需先排查服务，不要靠反复点击恢复期待清零。
