## 一、真实检索：本轮未自然复现 60 秒超时

从原第二章提取主查询及两个缺口查询，先串行再并发。探针设置 180 秒观察上限，便于观察是否超过生产的 60 秒阈值；没有修改项目配置。关闭服务侧查询缓存不表示模型、操作系统等其他缓存均处于冷态。

| 查询 | 串行总耗时 | 并发总耗时 | 串行重排耗时 | 并发重排耗时 |
| --- | ---: | ---: | ---: | ---: |
| 主问题：各细分板块生命周期及价值结构变化，附父研究主题 | 51.907 秒 | 47.625 秒 | 35.541 秒 | 45.982 秒 |
| 细分板块生命周期、成熟期、成长期、2026 | 19.343 秒 | 29.500 秒 | 18.700 秒 | 28.171 秒 |
| 价值结构重构、电子零部件占比、2030 | 11.953 秒 | 12.797 秒 | 11.406 秒 | 11.536 秒 |

六次均返回三条摘录、`cache_hit=false`。主查询候选 20 条，另外两条候选各 18 条；均重排 12 条。主查询首次召回阶段 15.660 秒，并发轮召回阶段 1.622 秒，因此不能仅比较总耗时就断言并发使主查询更快。重排计时来自服务响应，尚未拆分排队和推理。

测试期间知识服务 live/ready 均返回 200；容器只读检查显示未 OOM、重启次数为 0。两次 CPU 抽样约 490% 和 564%，说明当时多核负载较高，但不证明历史故障就是 CPU 排队导致。

**结论：**重排占主要耗时，主问题耗时已接近 60 秒阈值；部分查询并发时变慢。样本不足以估计超时概率或 p95/p99，也不能据此断言 10 月 3 日超时的具体根因。健康检查成功不代表重排检索能在 60 秒内完成。

## 二、真实章节链路：纠正生效，但仍有质量与成本风险

使用原第二章已有上下文，执行：检索 → 分析 → 写作 → 审校 → 改写 → 审校 → 结论/证据绑定。生产检索调用超时仍为 60 秒。

结果：

- 本次检索节点 49.750 秒完成，章节结果从 8 条增至 23 条。
- 共 6 次检索调用、8 次模型调用；服务返回的累计 Token 用量为 111,278，无未知模型用量。
- 最终草稿 2,455 字符、8 条结论，进入 `advance`，章节状态为 `limited`，不是无条件审校通过。
- 证据绑定第一次有两处 `evidence_quote_not_found`，第二次仍有一处，第三次通过业务校验。
- 三次绑定调用分别使用 14,138 / 16,923 / 16,711 Token，共 47,772，约占本次章节用量 43%。其中两次被拒绝的调用合计 31,061 Token。

**已经验证的修复效果：**原文摘录不匹配不再立即退出；业务错误进入统一纠正环路，错误定位到具体 Claim 和字段。此次第三次成功，但有限重试不保证以后每次成功。

**质量观察：**模型审查提出资料时效、单一来源、全球与中国统计口径错配、缺少指定细分板块直接证据等问题。流程在检索和修订轮数用尽后披露局限并继续；这些是模型提出的待核实问题，不是本测试完成了外部事实核验。输出有合法引用、准确原文定位，不等于全部事实判断已获充分支持。

对应设计：

- `sections/workflow.py:227`：补检轮数用完，即使分析结果为 revise，也转写作。
- `sections/workflow.py:305`：需要新证据但补检额度用完时，仍可能执行一次仅改写；文字修订无法替代缺失的证据。
- `sections/model_output.py:180` 附近：每次纠正重新提交原任务/来源及上一份答案，要求完整重生成；不是只修复错误字段，增加调用成本。代码仅保留上一次错误输出，不是无限累积所有失败答案。
- `sections/workflow.py:205`：直接将不同来源的 score 混排取前 15，无显式日期、来源多样性、缺口覆盖约束。这是代码可见的筛选风险；本实验没有证明被筛掉的资料一定更好。

## 三、真实成功结果 + 受控失败：复现丢失与重复检索

不是自然超时测试：保留主问题的真实知识检索；待其成功后，明确注入兄弟查询的 `CallTimeout`。关闭该测试进程中的 Web 分支，连续执行同一章节检索两次，其他生产进程不受影响。

| 执行 | 真实主查询返回 | 注入异常后的章节状态 | 累计真实主查询次数 |
| --- | ---: | --- | ---: |
| 第一次 | 3 条摘录 | 与执行前一致，无新结果提交 | 1 |
| 第二次 | 3 条摘录 | 与执行前一致，无新结果提交 | 2 |

两次均得到 `CallTimeout`、`state_unchanged=true`。第二次不是复用第一次的三条结果，而是再次请求真实服务。

原因：检索服务等待整批 `gather_cancel_on_error` 成功才整理结果，章节工作流在整个检索调用返回后才合并。已有章节 Checkpoint 不能替代节点内部的逐查询成果存储。

本组测试验证的是实际函数的结果提交边界和重复请求，不是 PostgreSQL 断电恢复测试；没有对原 Run 的持久化预算做预留或结算。

## 优先修复顺序与验收

1. **逐查询成果保存与恢复复用。** 请求使用明确的 Run/章节/轮次/查询标识，保存结果、失败类别、耗时和尝试次数。成功结果即使兄弟请求失败也保留。验收：本报告第三组场景恢复时不重复调用已成功查询。
2. **检索故障与预算耗尽分开处理。** 暂时故障进入可恢复等待/有限重试，而不是任一超时终止整个研究；重试仍计入总预算。区分知识服务、Web 并发，考虑服务端实际吞吐；不要仅靠无限重试或延长超时。验收：强制超时仍保留草稿和部分成果，已到预算上限时不再发请求。
3. **明确跨天恢复的时间预算语义。** 原案例绝对截止时间已过，不能靠再次点击恢复解决。应明确累计执行时长和任务有效期，或提供有审计、明确授权的预算扩展；不能静默重置已用额度。验收：暂停跨天和预算真正耗尽有不同结果，前端提前解释阻止原因。
4. **降低模型纠正和证据不足的成本。** 评估稳定摘录 ID/可选原文片段、较小 Claim 批次与局部修复；保留确定性原文校验。按证据覆盖选择来源，缺少新证据时允许输出“待补证据”，避免无效重复改写。局部修复也必须保持未修复结论、反证与引用一致性。
5. **形成可重复的验收矩阵。** 单 Run 长查询、并发 Run、依赖超时、模型连续非法输出、跨天恢复、持久化失败、进程中断分别测试。真实服务抽样和受控故障各自记录，不能互相替代，也不以一次通过声称稳定性已解决。

## 复现方式

脚本 `scripts/reproduce_retrieval_case.py` 是手动诊断入口，不会被普通 pytest 自动执行。当前固定读取上面的原案例；如果原 Run 后续变化，输入也会变化。原报告结果是当时旧节点链路的历史记录；当前 `chapter` 模式已改走 EvidenceResearchAgent、Writer、Reviewer 和 ClaimBindingProcessor，不再调用已删除的独立 `analyze` 节点。调用 `chapter` 会产生模型及外部检索费用；`probes`/`partial-failure` 不调用模型。

```powershell
$env:LANGCHAIN_TRACING_V2='false'
$env:LANGSMITH_TRACING='false'
$env:PYTHONIOENCODING='utf-8'
& 'D:\anaconda\envs\multi-agent\python.exe' -u -m scripts.reproduce_retrieval_case probes
& 'D:\anaconda\envs\multi-agent\python.exe' -u -m scripts.reproduce_retrieval_case chapter
& 'D:\anaconda\envs\multi-agent\python.exe' -u -m scripts.reproduce_retrieval_case partial-failure
```

JSON 行输出区分 `query_done`、`model_attempt`、`partial_failure` 和 `original_unchanged`。不要仅凭进程退出码判断研究成功：诊断脚本会捕获预期实验错误并输出其类别。完整生产 Run、多实例端到端、服务重启、持续负载和事实正确性均未在本轮验收。
