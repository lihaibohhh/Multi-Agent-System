# 章节研究改造：阶段一交付与后续计划

## 定位

支持分章节研究、证据补充和局部修订的专题研究系统，而非不断累积聊天历史的通用聊天机器人。

## 阶段一：串行章节闭环（已实现）

- 短问题允许单章；复杂问题由规划节点拆为 1–4 章，综合章只能位于末尾。
- 每章有独立问题、检索结果、选用来源、草稿版本、分析、审校和局限性。
- 流程为计划 → 当前章检索 → 证据分析 → 写作 → 审校 → 下一章 → 装配。缺证据可以回到本章检索，不重做已完成章节。
- 默认每章最多 2 轮收集、初稿后最多 1 次修订，策略保存在 Checkpoint。综合章首次复用前章证据也计一轮。
- 写作输入只包含当前章选用的摘录、提纲、前章摘要交接、父 Run 的短参考以及需要修改的本章草稿；不是全局消息历史。
- 后续综合章在前章全部处理完后执行，属于协调流程里的强依赖步骤。其他研究章目前也串行，不声称已实现并发或一般依赖 DAG。
- 整篇由代码按提纲拼接，局部引用编号映射为全局编号，同一证据去重；旧草稿与当时的来源映射一并保存。
- Run 查询包含 `sections`；SSE 增加 `section_plan`、`section_progress`、`section_snapshot`。页面可展开查看中间章节。
- 单节点出错后可恢复；已落盘的前序章节不重做。Run 数据库中的章节是展示快照，Checkpoint 是执行恢复依据；恢复事件可以修复两者短暂不同步。
- 新任务用版本 2，旧 Supervisor 节点保留。父子 Run 仍使用已有文本快照，尚未升级为结构化证据继承。

## 配置与运行

使用 `multi-agent` Conda 环境；在 `.env` 中设置：

```ini
AGENT_SECTION_MODEL=deepseek/deepseek-chat
AGENT_SECTION_MAX_COUNT=4
AGENT_SECTION_MAX_SEARCH_ROUNDS=2
AGENT_SECTION_MAX_REVISIONS=1
```

合法范围分别是 1–4 章、1–4 轮、0–3 次修订。恢复沿用已保存的次数策略，不会因修改环境变量而重置。生产恢复需要 SQLite/PostgreSQL Checkpoint，MemorySaver 仅适合调试。

API 不变：创建 Run → start → 读取事件；失败后调用原 Run 的 resume。没有新增“人工修改已完成章节”的接口，该能力在下一阶段实现。

```powershell
conda run -n multi-agent python -m pytest -q
conda run -n multi-agent python -m uvicorn multi_agent_research.api.server:app --host 127.0.0.1 --port 8000 --loop multi_agent_research.api.event_loop:selector_loop_factory
```

启动 API 时会对本项目 `research_runs` 表执行幂等的新增 `sections JSONB` 列操作，不读写隔壁知识库文件。检索继续通过 knowledge-service，固定 `use_query_cache=false`。

## 验收与已知限制

自动测试使用替身模型与检索结果，覆盖真实 LangGraph 路由、SQLite 关闭后重新创建图的恢复、补证/改稿次数限制、零证据、错误引用、SSE，以及 Run 持久化异常。PostgreSQL 往返测试需显式开启；真实模型质量、真实数据库升级和浏览器交互还需部署环境验收。

- 引用校验确认编号存在且至少有引用，语义支持关系仍依赖模型审校；还没有逐 Claim 的可审计证明。
- 证据不足或审校仍有问题的报告会标为 `limited` 并保留警告；编号越界在重试耗尽后会失败。恢复不能保证修复同一份无效输入。
- 选用来源按相关性最多 15 条；综合章的跨章来源覆盖尚无配额策略。
- Token 统计不涵盖所有失败请求和提供商重试；模型调用次数有界不等于严格金额上限。字符截断也不等于精确 Token 预算。
- 每次章节事件携带完整快照，优先保证简单可靠。随着章节/来源增多，需要改为产物引用或增量事件以降低存储开销。
- 尚无独立全篇语义审校、人工提纲确认、任意章节依赖、真正并发执行或完成后的局部编辑入口。

## 阶段二：证据关联与可控局部修订（下一阶段）

1. 增加轻量 Claim/Evidence 关联：结论指向原始摘录及文档、页码、chunk_id/URL，保留反证和不足，不从参考来源文本猜恢复证据。
2. 提供指定章节的补证/修订入口，保存版本；明确哪些下游综合内容变旧，不能把旧结论当成仍有效。
3. 增加全篇一致性审校：重复结论、时间/单位/范围冲突、不同章相反结论，以及研究问题是否覆盖完整。
4. 父子 Run 交接改为按需选择的结论、证据和待解问题；父证据仍标明来源与核验时间，不能假设永远有效。

验收重点：只改某章不重写无关章节，关联结论能定位原文，依赖的综合章正确失效并重建。

## 阶段三：依赖调度与共享预算

在章节与证据契约稳定后，显式记录依赖和任务边界；仅并行执行无依赖章节，综合/交叉审校/装配留在协调流程。增加全 Run 的 Token/费用预算、检索并发限制、任务取消、重试策略和产物级事件，避免并行放大负载。

每阶段完成后先汇报变更、验证结果和下一阶段范围，不把整套系统一次性重构完。
