# 章节研究改造：阶段交付与后续计划

## 定位

支持分章节研究、证据补充和局部修订的专题研究系统，而非不断累积聊天历史的通用聊天机器人。

## 阶段一：串行章节闭环（已实现）

版本 2 引入 1–4 章的计划、逐章检索/分析/写作/审校、草稿版本、引用装配、Run 查询与 SSE 章节快照，以及 SQLite/PostgreSQL Checkpoint 恢复。对应节点保留，历史任务不强制升级。

## 阶段二：证据关联与可控局部修订（已实现）

新任务为 `workflow_version=3`，新增以下能力：

1. 每章抽取 1–12 条关键 Claim，关联正文原文、来源原文、支持/反对/背景关系和不确定性。程序生成 Claim ID 与 Evidence ID，检查引用编号、原文是否真实存在于给定摘录；支持关系仍由模型判断，不保证全部事实句均被覆盖。无证据章节不伪造 Claim。
2. 新增章节修订 API 和页面入口。修订创建新的子 Run，保持父 Run 不变；目标章和传递依赖先标记 `stale`，新证据集清空，旧稿及其来源/Claim 保留为版本历史。每次修订单独限制检索/改稿次数。
3. 新流程的普通研究章不读取无关前章摘要；综合章明确依赖前章。持久化 `depends_on` 和 `dependency_revisions`；任何过期依赖阻止全篇装配。第一阶段的提示包含所有前章摘要，因此修订旧产物时保守重建目标后的章节。
4. 全篇一致性审校检查结论冲突、时间/单位/范围不一致、重复、问题覆盖。审校在所有章节完成后执行，是协调流程的强依赖步骤；发现问题则将报告标为 `limited` 并展示问题，不擅自改写其他章节。
5. 普通子 Run 的父上下文可以选择章节，传递真实检索摘录、Claim 和未解决问题。规划节点再按本章需要选择父章节；继承来源标明 `inherited_from_run`，不能假装刚刚重新检索。`retrieved_at` 是检索时间，不是文档更新时间；`reviewed_at` 是模型审校时间，不是独立事实核验时间；历史时间未知则保留未知。
6. 父交接和章节版本完整持久化，模型只看选择后的视图。前章交接仅摘要与不足；父结论视图每章最多展示 6 条，明确标记省略数量，不将全部历史草稿注入模型。新证据仍通过 knowledge-service 检索，固定 `use_query_cache=false`。

### 使用方式

使用 `multi-agent` Conda 环境。API 启动时为本项目 `research_runs` 表幂等增加 `report_review JSONB`；请先备份本项目数据库。没有修改隔壁服务、知识库或其配置。

普通创建、start、SSE、resume 接口保持不变。指定章节修订：

```http
POST /api/runs/{已完成的父run_id}/sections/{section_id}/revisions
Content-Type: application/json

{"instruction": "补充最新年度数据并检查相反证据", "run_id": "可选的新ID"}
```

返回 `201` 和 `created` 子 Run，创建本身不调用模型。待重建清单位于 `parent_context.revision_sections`；随后调用新 Run 的 `/start`。新 Run 失败后使用自己的 `/resume`。原报告和原 Checkpoint 不变。不存在章节返回 422，不存在 Run 返回 404，未完成父 Run 返回 409。

页面：打开已完成报告 → 展开章节 → 填写修订要求 → 创建修订 Run → 核对待重建章节 → 启动。

普通子 Run 可在 `POST /api/runs` 中增加 `parent_section_ids: ["section_1"]`。省略表示保存所有父章节供后续规划选择，空数组表示不提供章节；不能在没有父 Run 时使用。没有章节产物的外部历史报告只能作为文本快照参考，不支持局部修订。

SSE 新增 `report_review`；`section_progress` 增加 `section_claims` 阶段。Run 查询返回 `sections[*].claims`、历史草稿及 `report_review`。恢复时同步两类产物以修复 Checkpoint 与业务展示之间可能的短暂不同步。

### 配置与次数限制

```ini
AGENT_SECTION_MODEL=deepseek/deepseek-chat
AGENT_SECTION_MAX_COUNT=4
AGENT_SECTION_MAX_SEARCH_ROUNDS=2
AGENT_SECTION_MAX_REVISIONS=1
```

合法范围：1–4 章、1–4 轮收集、0–3 次初稿后的自动修订。综合章首次复用前章证据也计一轮。恢复沿用已保存的策略；新修订 Run 使用新的章节收集/修订轮次限制，章节版本号持续递增。模型调用、检索调用与 Token 只累计到当前 Run 的独立预算账户。

每个有证据章节新增一次关键结论抽取调用，每份报告新增一次全篇审校调用。2026-10-08 已将 Claim 更新为逐条接受与局部修复：保留通过项，初次抽取和修复共用本次三次额度，耗尽后保存待修复项并暂停；明确继续时累计研究预算不清零。其他节点仍使用有界整体纠正。详见 [Claim 局部修复](claim-local-repair.md) 和 [模型输出与恢复修复](model-output-recovery.md)。

### 验收与已知限制

自动测试使用替身模型和检索，执行真实 LangGraph 路由、SQLite 重启恢复以及 Run 服务。覆盖目标章节修订、未受影响章节原样保留、综合章失效重建、重复修订的次数限制、零证据旧稿归档、伪造摘录拒绝、反证保留、父快照不可变、全篇冲突披露、API 创建/执行分离以及版本 2 兼容。

本阶段离线验收：Python 78 项通过、PostgreSQL 集成测试 1 项按配置跳过；Node DOM 契约测试 3 项通过。后者检查文本安全展示、创建修订操作和 SSE 完成后的界面逻辑，不替代真实浏览器视觉验收。

```powershell
conda run -n multi-agent python -m pytest -q
node --test tests/test_demo_sections.cjs
```

仍需在部署环境验收真实模型效果和 PostgreSQL 升级/往返；默认测试不调用真实知识服务或付费 LLM。可选 PostgreSQL 测试已增加审校与修订快照字段的往返检查，但不默认执行。

- Claim 是关键结论索引，不是逐句穷尽证明；程序核对的是给定摘录，不是完整原文或外部真实性。
- 全篇审校只报告问题，不自动寻找最小修复集；需要用户选择章节再发起修订。
- 当前依赖限于有序章节，独立章无前章依赖，综合章依赖前章；不是通用动态 DAG 调度器，仍串行。
- 修订旧版报告时，未受影响的旧章节不会为了补齐 Claim 而重写，仍保留其原来的产物版本；新写或重写的章节才走新版结论抽取。
- 来源按相关性最多选 15 条，综合章尚无跨章配额；长摘录按 1000 字符限制模型输入，实际检索适配器还可能更早裁剪。
- 父视图有字段级限制，但还没有精确的全 Run Token 预算。新增 `model_usage` 持久化章节模型各次调用的已知用量，包括校验失败及格式纠正；历史调用、底层 SDK HTTP 重试与取消后未收到的用量仍可能缺失，不是完整账单或金额上限。
- 完整章节事件与历史版本会占用存储；下一阶段应逐步改为产物引用/增量事件，避免长期修订链不断增大。

## 阶段三：依赖调度与 Run 独立预算（可靠性加固后）

在进入并行改造前，增加两个可靠性阶段：

- 链路加固第一阶段：统一格式/业务校验、共享纠正预算、引文原文定位和完整错误记录，已实现；详见 [交付说明](business-validation-hardening.md)。
- 链路加固第二阶段：启动事务、失败补偿、单实例所有权、失联任务对账、旧执行写入隔离和持久化能力检查，已实现；详见 [运行与恢复可靠性](runtime-reliability.md)。原 Run 恢复仍需部署后单独执行。

研究预算 v3、有界调用、跨 Run 检索并发上限和取消传播已实现，见 [预算阶段交付](run-budget.md)。当前版本采用每 Run 独立预算账户、按执行计时、安全暂停、跨天继续、显式旧账迁移，并自动把旧共享账户按 Run 账目拆分。第二阶段已实现逐查询保存、成功成果复用及有限重试，见 [恢复验证](retrieval-recovery.md)。第三阶段已实现 [章节选择式继续、仅补证据和刷新来源](section-operations.md)，子 Run 保留授权范围内的原产物但不继承费用账本，并区分阶段结果和完整报告。下一阶段先做真实案例闭环验收、局部纠正和可审计恢复控制，再落实 ResearchTask/并行调度；当前章节继续串行执行。Token 准入使用预留估计，不是严格金额保证。

1. 固化 ResearchTask 的输入/输出边界，先增加全 Run 预算、检索并发上限与取消传播。
2. 仅并行无依赖章节，综合章、全篇审校和最终装配继续由协调流程等待前置产物。
3. 为任务重试、部分失败、并发恢复建立明确规则；完善费用/Token 统计与结构化产物事件。

验收重点：多个独立章节并行但预算不超额；部分失败不丢已完成产物；有依赖的步骤不提前执行。每阶段完成后汇报结果和下一阶段范围，不一次性重构全部系统。
