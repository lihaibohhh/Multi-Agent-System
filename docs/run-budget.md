# Run 独立预算与暂停继续（v3，2026-10-09）

## 第一阶段：已实现

研究成果可以跨天存在；每次执行独立计时，同一个 Run 的累计额度不会因暂停或恢复而重置。父子 Run 可继承研究产物，但预算账户严格隔离。

### 预算归属

- 新独立 Run 创建研究预算账户 `research_budget_accounts`，Run 通过稳定的 `budget_id` 引用。
- 每个新 Run（包括通过 `parent_run_id` 创建的继续、补证据和修订 Run）都创建自己的预算账户；Session、研究树和父子关系不再决定预算归属。
- 账户策略在创建时快照，改环境变量不改变已有额度。子 Run 获得新 Run 的完整默认额度，但父 Run 的历史消耗不会计入子 Run，子 Run 消耗也不会回写父 Run。
- 预算是业务数据库中的独立账本，不从 Checkpoint 恢复或回退。章节图中的 Token 指标仅是进度指标；账户累计是准入依据。
- 账户在事务中锁行预留。预算明细标记 Run/执行批次；旧执行不能结算新执行或其他 Run 的请求。

### 旧共享账户隔离

仓储启动时会检测仍被多个 Run 引用的历史 `budget_id`，并在逐账户事务中按
`reservation.run_id`、`model_usage`、检索回执和 `budget_increased` 事件拆分账本。
每个 Run 获得稳定的新账户 ID；已有消耗、未知预留和该 Run 自己的追加额度均保留。
无法精确归属的历史聚合余量只保守归入最早 Run，并标记 `history_incomplete`，不会凭空
复制给所有子 Run。旧账户不删除，保留作审计和回滚依据。

维护命令 `python -m scripts.isolate_run_budgets` 默认只读预览；增加 `--apply` 才执行。
迁移幂等，且不会启动/恢复研究或调用模型、检索服务。生产执行前仍应备份
`research_budget_accounts`、`research_runs`、`research_run_events` 和
`research_retrieval_operations`。

### 时间与停止状态

| 配置/状态 | 含义 |
| --- | --- |
| `AGENT_RUN_MAX_MODEL_CALLS=80` | 单个 Run 累计模型调用，含纠正及失败请求 |
| `AGENT_RUN_MAX_TOKENS=500000` | 已知用量 + 未结算预留的准入阈值 |
| `AGENT_RUN_MAX_RETRIEVAL_CALLS=80` | 单个 Run 的知识服务与 Web 累计调用，含网络重试 |
| `AGENT_RUN_TIMEOUT=3600` | 每次执行最长一小时，显式继续重新计时，不含此前离线时间 |
| `AGENT_MODEL_CALL_TIMEOUT=120` | 单次模型调用超时 |
| `AGENT_RETRIEVAL_CALL_TIMEOUT=60` | 单次检索调用超时，不含等待本地并发槽位 |
| `AGENT_RETRIEVAL_CONCURRENCY=4` | 当前 API 进程所有 Run 共享检索槽位 |
| `paused` / `run_paused` | 用户暂停、本次执行时限到达或暂时检索故障；事件 reason 区分原因，可继续 |
| `budget_limited` / `budget_limited` | 累计额度不足；普通恢复不增加额度 |
| `failed` | 模型错误、不可自动重试的检索响应、单查询累计尝试耗尽等 |

每次认领执行更新 `execution_id` 和 `execution_deadline`，启动/恢复事件保存它们。API 中的 `budget.deadline` 是兼容展示字段，表示该 Run 最近一次执行时限，不是研究永久有效期。账户本体没有这一次执行的截止时间。

启动/恢复会预检模型次数及 Token 额度，已耗尽时返回 409，不进入图。对于这两项，预检仍保守，不尝试纯装配路径。检索额度已满允许进入恢复以复用已保存查询，但任何新检索仍被原子预算检查拒绝。执行中的纯装配和检索成果重放不新增调用、不额外收费；不能依赖前端按钮作额度保护。

### 安全暂停

`POST /api/runs/{run_id}/pause` 返回 202，表示暂停请求已持久化，并非已经停稳：

1. 通过与预算预留相同的 Run 行锁设置 `pause_requested`，之后不再批准新外部调用。
2. 已批准的调用有机会在调用/本次执行时限内完成和结算；取消或用量未知保留预留。
3. 在可保存的步骤边界关闭图事件流，等待内部检查点写入收尾，再发布 `run_paused`。
4. 前端先显示“正在暂停”，收到终态后显示“已暂停”，此时才可继续。
5. `POST /api/runs/{run_id}/resume` 沿用 Run ID、预算账户和 Checkpoint，只新建执行批次。

关闭网页不自动暂停。暂停请求提交前已被批准的网络请求，可能在提交后才实际发送；本地取消不保证远端停止或不计费。若暂停恰逢最后完成，任务可能正常完成；若同时遇到真实故障，仍如实显示该故障。服务器崩溃后由已有执行对账机制标记中断，不自动启动第二个执行者。

### Token 账本

可用额度 = 当前 Run 授权总额度 - 当前 Run 已确认消耗 - 当前 Run 未结算预留。获取返回用量后幂等结算；重复结算不增加或回退费用。同一个 Run 内的所有章节和纠正调用使用同一账本；父子 Run 之间不共账，上下文压缩也不抵销本 Run 历史费用。

预留仍使用 UTF-8 字节数、协议余量和模型输出上限作估计，不是精确 tokenizer 或账单金额。实际返回超出估计时记录真实用量并阻止后续越额请求，不能承诺物理 Token 绝不超过上限。预留成功但发送前进程退出会保守占用额度；未知用量不会随恢复自动退款。

预算不足时只能对当前 Run 做明确、可审计的额度调整。创建子 Run 会获得独立额度，但它代表新的研究执行和成果版本，不能冒充原 Run 的断点恢复；普通恢复仍沿用原 Run 账本。单独 CLI/直接调用图不具备 API RunService 的持久化预算账户保证。

## 旧 Run：显式迁移，不静默清账

启动新版本只增加账户表、关联列、执行时限和暂停字段，以及扩展状态约束。不会自动给历史 Run 创建新预算或更改旧绝对截止值。

旧 Run 没有 `budget_id` 时，启动/继续被拒绝。页面“确认迁移旧预算策略”或以下接口可以显式迁移：

`POST /api/runs/{run_id}/budget/migrate`

请求示例：

```json
{"confirm": true, "reason": "确认改为每次执行独立计时，并保留原累计消耗"}
```

- 迁移仅允许非 running Run；重复请求幂等。
- 完整复制旧账户额度、已用次数、已知用量和未知预留，只改变时间策略版本。
- 保留 `research_runs.budget` 里的原始旧账；事件记录原因、旧/新摘要和新账户 ID。
- 更老的空预算仅导入可见 `model_usage`，明确标记历史统计不完整；不能凭空还原历史未知费用。
- 历史父子 Run 原来各有独立额度，迁移时明确以“这个历史 Run”为边界，不自动合并、不追溯新增额度。迁移后新建的子 Run 仍创建独立账户。
- 迁移不会改章节/报告、不会启动研究、不会突破已耗尽的 Token 或调用额度。迁移后用户另行点击继续。

部署需先备份本项目业务库与 Checkpoint，停止旧版 API，再使用 multi-agent 环境启动单实例单 worker，刷新页面。不要混跑旧版和新版服务；旧代码不理解新账户。迁移后的新消耗在账户表，不能直接降级旧代码或只恢复旧 Run 行来替代完整数据库恢复。

## 第二阶段：逐查询保存与恢复复用（已实现）

- 新增本项目表 `research_retrieval_operations`，按 Run、章节版本、轮次、提供方、查询内容和相关参数隔离成果。不是知识库查询缓存，不写隔壁服务；请求仍固定 `use_query_cache=false`。
- 发起一次尝试时，检索操作、请求额度预留、进度事件在同一事务提交；提交失败不发送外部请求。成功时结果、预算结算和事件也原子提交。
- 每条成功查询独立保存标准化结果，包括成功的空列表和原检索时间。恢复重放不新增 HTTP 请求、不再扣检索额度，也不伪装成今天重新检索。
- 同批的暂时/永久依赖错误会等待其他查询完成并保存，再停止节点。预算、数据库或执行所有权等控制错误仍可取消其他未完成请求；已保存成功结果不丢。
- 单查询策略首次创建即保存：每次执行最多 2 次尝试（初次 + 1 次自动重试），跨恢复累计最多 4 次，重试前等待 1 秒。每次实际尝试还受研究总额度、调用超时、执行时限和全局并发限制，不嵌套 Web 适配器重试。
- 超时/连接故障及知识服务 HTTP 408、429、5xx 视为暂时故障。单次执行尝试用完后，Run 为 `paused`，`reason=dependency_unavailable`，由用户稍后继续，不后台无限轮询。累计 4 次耗尽后 `failed`，再次普通恢复不会发送该查询；没有暗中清零或追加额度。
- 鉴权、其他 4xx、解析及格式错误不自动重试；修正配置后可手动继续，但仍沿用剩余累计尝试。错误不再静默转为空结果；缺失 `chunks` 字段也不算成功。
- 请求超时、取消或进程崩溃时不能确认远端是否已执行，保留原预算预留。恢复后允许新的有界尝试；旧执行及旧尝试不能覆盖新成果。
- SSE `retrieval_progress` 展示保存/复用状态、结果条数和累计尝试；数据库保留每次执行批次、预留 ID、时间、错误类型。完整查询和来源内容留在本项目结果表，不重复塞进进度事件。

真实案例与验收见 [逐查询恢复验证](retrieval-recovery.md)。普通启动/恢复 API 不变，使用新代码启动 API 时幂等增加结果表；不需要额外迁移历史成果。历史失败节点中从未落库的查询结果无法追溯补回，第一次新版恢复可能仍要重查；已有章节 Checkpoint 继续保留。

这不是外部请求 exactly-once 保证：远端已完成、本地结果未提交就断电，恢复仍可能重复请求并累计收费。也没有解决知识服务本身的排队/重排延迟。仅 API RunService 绑定持久化预算上下文时有这一保证，CLI/直接调用图仍不是同等级的恢复路径。

## 第三阶段：章节选择式继续与证据更新（已实现）

1. 定义用户选择未完成章节、仅补证据、修订章节的明确操作边界，检查依赖及下游失效范围。
2. 普通恢复保留原检索成果；只有明确刷新或新研究轮次才发新请求，保留历史来源和检索时间。
3. 证据不足进入可解释的待补状态，支持局部纠正，不为了继续而放松原文校验。
4. 新操作创建独立 Run 预算；研究产物、检索回执和失败尝试按操作规则继承，但父子费用不混算。

具体操作、阶段产物语义及后续计划见 [章节局部操作](section-operations.md)。暂不增加并行章节调度，也不自动执行历史 Run、预算充值或清除未知预留。
