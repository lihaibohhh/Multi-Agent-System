# vLLM 学习与实践总结

> 历史实验归档：文中旧 `analyst_agent` 生产链路已经删除，内容仅保留实验结论，不再是可执行说明。

> 涉及环境：WSL2(Ubuntu) + RTX 3060(12GB) + vLLM，测试模型 Qwen2.5-1.5B-Instruct / Qwen2.5-7B-Instruct-GPTQ-Int4

---

## 一、核心概念

### 1. KV Cache 与显存浪费问题

模型每生成一个新 token，都需要用到之前所有 token 算出的 Key/Value 向量做 Attention 计算。为了避免每次都重新计算，工程上把这些 K/V 缓存下来，这就是 KV Cache。问题在于：推理开始时不知道这次对话最终会生成多长，传统做法只能按"最大可能长度"提前预留一整块连续显存，而实际生成长度往往远小于这个上限，导致大量显存被白白预留却用不上——这正是传统推理方式显存利用率只有 20%-40% 的根源。

### 2. PagedAttention：借鉴操作系统分页思想

操作系统的虚拟内存分页解决过同样的问题：不再分配连续物理内存，而是把内存切成固定大小的"页"，按需分配、用完回收，物理上不连续也没关系，靠"页表"维护逻辑到物理的映射。PagedAttention 把这套思路原样搬到 KV Cache 管理上：把 KV Cache 切成固定大小的"块"（vLLM 里的叫法是 block，跟 OS 的 page 是一个意思），按需分配给请求，用完立刻回收给别的请求用，靠"块表"维护映射。这让显存利用率从 20%-40% 提升到接近 90%。因为一个请求的 K/V 散落在不同的物理块里，vLLM 还专门写了定制的 CUDA kernel 来处理这种"分块读取再拼接"的 Attention 计算，这也是"PagedAttention"里"Attention"的来源。

### 3. Continuous Batching：按需调度，告别"陪等"

传统静态批处理要求一批请求同时开始、同时结束——跑得快的请求结束后只能空闲等待，直到最慢的请求结束才能放下一批新请求进来，这段空闲时间 GPU 算力被浪费。Continuous batching（也叫 iteration-level scheduling）按"每一步"做调度：请求结束立刻让出位置，新请求立刻插入，批次始终是满的。这个能力依赖 PagedAttention 的支撑——因为显存是按块管理的，新请求加入时只需要分配几个空闲块，不需要找一整块连续显存，两者是互相成就的关系。

### 4. 面试一句话总结

> 传统方式按最大长度预留连续显存，但实际生成长度不确定，大部分预留空间用不上；PagedAttention 借鉴操作系统的分页思想，把 KV Cache 切成固定大小的块按需分配、用完回收，显存利用率从 20%-40% 提升到接近 90%。配合 continuous batching 按每一步做调度，请求结束立刻让位、新请求立刻插入，整体吞吐显著提升。

## 二、部署与压测实验

### 1. 环境与做法

WSL2 + `vllm serve Qwen/Qwen2.5-1.5B-Instruct`，暴露 OpenAI 兼容接口。用 `AsyncOpenAI` 客户端写了一个并发压测脚本，对比"串行依次发送"和"并发同时发送"两种方式在不同请求数（n=8/32/64/128）下的真实吞吐量（总生成 token 数 ÷ 总耗时），不依赖服务端日志里那种容易被空闲时间稀释的平均吞吐数字。

### 2. 实验数据

| 并发数 n | 串行吞吐量 | 并发吞吐量 | 提升倍数 | 并发模式平均单请求延迟 |
|---|---|---|---|---|
| 8 | 45.49 tokens/s | 325.97 tokens/s | 7.17x | 0.37s |
| 32 | 69.06 tokens/s | 622.04 tokens/s | 9.01x | 0.64s |
| 64 | 72.68 tokens/s | 988.90 tokens/s | 13.61x | 1.01s |
| 128 | 72.91~73.31 tokens/s | 1138.95~1272.87 tokens/s | 15.5x~17.46x | 1.63~1.73s |

### 3. 关键发现

**串行吞吐量很快趋于一个平台**（约 73 tokens/s），这个数字就是"单请求顺序执行"时这块 GPU 跑这个模型的真实算力上限，跟并发数无关。

**并发吞吐量的边际收益递减**：每多发一个并发请求带来的吞吐贡献在持续下降（n=8 时约 40/请求，n=128 时只剩约 10/请求），说明 GPU 正在逼近并发容量上限。

**吞吐与延迟的权衡**：并发数越高，单请求延迟也越高（0.37s → 1.73s），这是 vLLM 调度策略的天然取舍——用"略微增加单请求延迟"换"大幅提升整体吞吐"，适合高并发、不太在乎单次响应快慢的场景（如批量离线评测）。

**Prefix Caching 的额外发现**：日志里出现 `Prefix cache hit rate: 68.5%`，因为压测脚本里每个请求的 system prompt 完全相同，vLLM 识别出重复前缀直接复用了之前算好的 KV Cache，不用重新计算——这是分页式 KV Cache 管理顺手带来的额外收益（块可以被多个请求共享引用）。

**一个真实的"反向验证"小插曲**：曾尝试把 `max_tokens` 从 150 调到 300 想拉长压测时间以捕捉 `Waiting > 0` 的瞬间，结果耗时几乎没变——因为模型本来就没顶到旧的 150 上限，生成长度是模型自己决定的，调大上限不会改变实际行为。这本身是个有价值的负向结果。

## 三、接入 Multi-Agent 项目：Provider 集成

### 1. 现有抽象设计

项目里 `utils/llm.py` 已经是一个干净的工厂模式：解析 `"provider/model-name"` 格式的 `model_ref`，按 provider 分发到对应的构造函数，配置统一从 `settings` 读取。其中已经存在 `local` / `openai-compatible` 这个 provider 选项，底层就是指向可配置 `base_url` 的 `ChatOpenAI`——这跟 vLLM 暴露的 OpenAI 兼容接口完全是一回事，意味着接入 vLLM 几乎不需要写新代码，只需要把配置的 `base_url` 指向本地服务即可。

### 2. 发现的 bug

`_build_local_openai_compatible` 函数里有一行：
```python
api_key = cfg.base_url   # 应该是 cfg.api_key
```
对 vLLM 没有实际影响（vLLM 默认不校验 key），但如果以后用这个 provider 接其他需要鉴权的 OpenAI 兼容服务会直接出错。

### 3. 命名混淆

本地/vLLM 现在使用独立的 `settings.local` 配置段，通过
`LOCAL_LLM_BASE_URL`、`LOCAL_LLM_API_KEY` 和 `LOCAL_LLM_MODEL` 配置，
不再复用 Azure OpenAI 配置。

## 四、模型能力评估实验：DeepSeek vs 本地模型

### 1. 实验设计

不复制粘贴 `analyst_agent.py` 里的 prompt 拼接逻辑（容易写得不一致导致对比失真），而是直接 `import` 生产模块，调用真实的 `analyst_agent_node()` 函数，只在调用前临时把模块级的 `_structured_llm` 替换成指向本地 vLLM 的版本，跑完立刻换回去——两次调用走的是完全相同的一份代码，唯一变量是底层模型。

设计了三组对比鲜明的场景，用来检验本地模型是否存在系统性问题，而不是单一样本的偶然结果：

1. **原始真实样例**（7 条，来自一次真实的 `search_agent` 运行，分数 0.31~0.99）
2. **人工构造-信息明显充分**（6 条，针对 DeepSeek 之前指出的缺口逐条补齐）
3. **人工构造-信息明显严重不足**（2 条，低相关/离题内容）

### 2. 三场景对比数据（本地模型为 Qwen2.5-7B-Instruct-GPTQ-Int4）

| 场景 | DeepSeek | 本地模型 |
|---|---|---|
| 1. 原始真实样例 | revise / 0.70 | pass / 0.95 |
| 2. 信息明显充分 | revise / 0.70（换了更细的新缺口） | pass / 0.95（数字与场景1完全一致） |
| 3. 信息明显严重不足 | reject / 0.10 | revise / 0.50 |

### 3. Reason 字段深度分析（关键证据）

最初只对比 verdict/confidence 数字，发现场景 1 和场景 2 本地模型的输出完全一致，怀疑它没有真正读取内容差异。补上 `reason` 字段打印后验证了这一点：本地模型在两个场景下给出的理由本质上是同一句话换了几个近义词（"市场现状"↔"市场格局"），**没有提到任何场景 2 里特意加入的具体事实**（如"启言科技融资"、"好未来财报增长 65%"）。而 DeepSeek 在场景 3 甚至准确指出"来源 2 为在线少儿英语培训行业报告，但内容聚焦传统英语培训而非 AI 教育"——是真的在逐条核对来源具体写了什么。

### 4. 最终结论

本地这个 7B 量化模型能产出格式合规的结构化输出，在"明显很差"的极端情况下也能正确转向 revise/reject 方向，**判断方向基本正确，但做的是"主题覆盖度 checklist"式的浅层判断，而不是逐条核对具体事实、点名缺什么数据的深度批判性审查**。

**最终决定：不将本地模型接入 `analyst_agent` 生产链路**，原因是它缺乏 DeepSeek 那种基于具体事实的细粒度批判性推理能力。这是一次有数据支撑的探索性验证，得出"不采用"的结论本身也是工程判断力的体现，跟"成功接入并提速"的故事同样有价值。

## 五、可直接使用的面试/简历表述

> 在自部署的 vLLM 服务（Qwen2.5-1.5B-Instruct，RTX 3060）上设计并执行了并发压测实验，对比串行与并发场景下的真实吞吐量，验证了 continuous batching 配合 PagedAttention 分页显存管理带来的吞吐提升——128 并发下吞吐量达串行基线的 17 倍以上（73 → 1273 tokens/s），并观测到吞吐增益随并发数增加呈边际递减趋势。进一步探索了将本地 vLLM 模型作为 Multi-Agent 系统中 `analyst_agent` 的低成本备选 provider，设计了三组对照实验（真实样例/信息充分/信息严重不足）配合归因分析，发现本地量化模型的判断停留在主题覆盖层面、缺乏细粒度事实核查能力，基于数据做出了不采用的工程决策。

面试官大概率会追问、且现在应该能脱稿回答的几个点：
- 为什么传统推理方式显存利用率低，PagedAttention 怎么解决
- continuous batching 怎么进一步提升吞吐，为什么需要 PagedAttention 配合
- 为什么并发数越高吞吐提升的边际收益越小
- 怎么设计实验判断一个模型是否适合接入某个生产任务，而不是只看单次输出是否"看起来对"

## FastAPI — 3天

**第1天：把已经用过的东西真正搞懂**

你已经能写路由和接口，但大概率是照着 AI 输出的，不清楚背后的逻辑。这天的任务是把现有代码从头读一遍，搞清楚三件事：

FastAPI 怎么用 Python 类型注解 + Pydantic 自动做请求验证和序列化——你用 `BaseModel` 定义过请求体，但能解释为什么这样写吗？路由装饰器（`@app.get` / `@app.post`）和参数声明（path / query / body）的区别是什么？响应模型 `response_model` 的作用是什么？

做法：不看 AI，把多 Agent 项目里的某一个接口删掉，自己从空文件重新写出来，能跑通为止。

**第2天：SSE 和异步**

这是你简历里最容易被追问的点。面试官问"你的 SSE 是怎么实现的"，你现在能答到什么程度？

需要搞清楚的：SSE 是什么、和 WebSocket / 普通轮询的区别；`StreamingResponse` 和 `EventSourceResponse` 怎么用、为什么要用异步生成器；FastAPI 里 `async def` 和普通 `def` 的区别，什么时候用哪个。

做法：单独写一个最小的 SSE 示例，输入一句话，模拟逐字流式返回，不依赖项目代码。然后回头读你项目里的 SSE 实现，能逐行解释为止。

**第3天：依赖注入 + lifespan + 错误处理**

这三个是 FastAPI 里最"框架感"的部分，也是你目前不熟的。

依赖注入（`Depends`）解决什么问题——数据库连接、认证 token、配置读取，这些跨接口共享的东西怎么统一管理；lifespan 事件（`@asynccontextmanager` 写法）——你项目里 RAG 模型"仅预热一次"就是靠这个，现在能解释吗？`HTTPException` 和自定义异常处理怎么用。

做法：把项目里的模型预热逻辑找到，搞清楚它为什么要放在 lifespan 里而不是普通函数里。然后给某个接口加一个用 `Depends` 实现的简单参数校验。

## Docker — 2天

**第4天：Dockerfile 真正搞懂 + 基本操作**

你跟着 AI 写过，但"理解基本语法"和"能自己排查问题"之间还有差距。这天要达到的状态是：不看 AI，能给你的 FastAPI 项目从零写一个能跑的 Dockerfile。

需要搞清楚每一条指令的作用：`FROM` 选什么基础镜像、`WORKDIR` 为什么要设、`COPY` 和 `ADD` 的区别、`RUN` 执行时机、`CMD` vs `ENTRYPOINT`、`ENV` 和 `ARG` 的区别。还有 `.dockerignore` 是什么、为什么必须有。

做法：给多 Agent 项目的 FastAPI 服务写 Dockerfile，`docker build` 构建，`docker run` 跑起来，用 `docker logs` 看日志，用 `docker exec -it` 进容器查问题。把端口映射和环境变量传入搞清楚。

**第5天：Docker Compose**

你的项目天然是多服务的——FastAPI + Redis，这正是 Compose 的典型场景。

需要搞清楚：`docker-compose.yml` 的结构（services / ports / volumes / environment / depends\_on）；容器间怎么互相访问（服务名就是域名）；volumes 怎么挂载持久化数据；`docker compose up / down / logs` 基本命令。

做法：给多 Agent 项目写一个 `docker-compose.yml`，把 FastAPI 服务和 Redis 一起编排起来，`docker compose up` 能跑通整个系统。这个做完你简历上"熟悉 Docker"就真的成立了。
